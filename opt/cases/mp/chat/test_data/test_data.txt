# 被测对象：微信小程序（小量动机）

本项目测试的是微信小程序，不是网页。

## 工具路由

默认所有页面操作走 MCP 工具，工具名以 mmcp_wxmp_ 开头，target_helper 用 mcp。

浏览器工具（open_url、click、get_interactive_elements、get_page_text、geturl 等）
对小程序页面无效，不要用它们打开或操作小程序页面。

截图和视觉断言也走 MCP，不走浏览器：
- mmcp_wxmp_mp_screenshot 存证
- mmcp_wxmp_mp_visual_check 回答关于画面的问题
- mmcp_wxmp_mp_visual_compare 比对基准图

planner 的能力表把「visual validation」归给 browser helper，那一条在本项目不成立：
这里没有可用的浏览器上下文，浏览器截到的是空白页，不是小程序画面。
所以步骤里出现「在截图上确认…」「与基准图…一致」「看画面」时，
target_helper 依然必须是 mcp，绝不要因为它是视觉判断就切到 browser。

唯一例外：小程序内嵌 web-view 的 H5 页面。web-view 内部是独立的浏览器上下文，
MCP 工具够不到。这种情况先用 mmcp_wxmp_mp_webview_url 读出真实 URL，
再交给浏览器工具去测那个 URL。

## 操作方式

1. 每条用例开始，先用 mmcp_wxmp_mp_login_as 设置前置态：
   - logged-in：已登录用户（默认 `base` fixture 下昵称 Neo、用户ID user-001；
     用例先调了别的 fixture 时，登录身份以该 fixture 的资料为准，不必是 Neo）
   - guest：未登录
   不要去驱动登录界面，微信授权弹窗是原生 UI，自动化点不到。

2. 跳转页面用 mmcp_wxmp_mp_navigate，传路由名而不是路径。
   可用：首页 / 对话 / 我的 / 登录 / 量表 / 注销账号
   （英文名 home / chat / mine / login / luxxTest / unregister 同样可用）

3. 不确定页面上有什么时，先用 mmcp_wxmp_mp_snapshot 查看。
   它会列出当前页所有可见文案和控件。

4. 点击用 mmcp_wxmp_mp_tap_text，传可见文案（例如"退出登录"）。
   不要用 CSS 选择器或 class 名。

5. **断言一律用 `assert_ui`，不要读一遍快照自己判定。**

   先用 `mmcp_wxmp_mp_snapshot`（或 `mp_page_data` / `mp_get_text`）取回页面，把返回的
   原文整个交给 `assert_ui` 的 `payload`。四种 mode：

   | mode | 用在哪 |
   |---|---|
   | `contains` | 页面上应该出现某段文案 —— 默认用这个 |
   | `absent` | 某段文案应该消失 |
   | `count_eq` | 数量本身就是要求（恰好两条对话） |
   | `no_placeholder` | 渲染出来的是不是真数据 |

   `scope` 先把范围收窄到含某段文字的那些行，避免"列表里应该有 X"被页头上的同一个词满足。

   为什么不能自己读快照判定：判定和证据都留在模型的自述里，报告只能看到一句"通过"，
   事后没人能回答它到底断言了什么。`assert_ui` 每次调用都会写进
   `proofs/.../assertion_logs.log`，通过的也写——一条绿色用例因此可以审计。

6. **优先断言值，不要只数个数。**

   「昵称元素存在」在页面渲染出错误昵称时照样是绿的；`contains` 加上期望的昵称就不会。
   ESM 3.0 那批缺陷里最大的一类正是「数对了、内容错了」：对方昵称显示成默认「小量」、
   双人会话标题全叫「关系对话」、候选关系卡片文案写死设计稿。只有数量本身是需求时
   才用 `count_eq`。

   任何一步加载完内容之后，顺手再来一条 `no_placeholder`，成本极低：它抓 `undefined`、
   `[object Object]`、没替换的 `{{模板}}`、该渲染却裸露的 Markdown 记号、泄漏的 i18n key。
   页面特有的默认值（比如没被真实昵称替换掉的「小量」）写进 `forbidden`。

7. **`absent` 必须给正向对照，而且只对快照看得见的东西有效。**

   `assert_ui absent` 在「文本里没有」时通过，而「没有」的成因大多和被测方无关：页面还没
   渲染、抓错了屏、快照是上一页的。所以 `must_contain` 是必填的——点一件这一屏上本来就该
   有的稳定文案，证明这次确实看的是对的、已渲染的那一屏。

   更要紧的一条：**快照表示不了的东西，`absent` 恒真。** `mp_snapshot` 只收有文案、有
   aria-label 或可交互的节点，红点、角标、下划线、边框、选中态、纯图标这些无文案元素
   压根不在待检文本里，对它们写「不应该看到」不管缺陷在不在都会绿。这类判定走
   `mmcp_wxmp_mp_visual_check`（视觉模型判读 + 截图存证），或者先让前端给那个元素补上
   aria-label / testId 再改回 `assert_ui`。`lint_gherkin.py` 的 `unverifiable-absent`
   规则会在合入前拦下这种写法。

8. **跨页一致性用 `capture_ui_value` 抓值，不要自己抄。**

   「A 页改了值，B 页有没有同步」这类用例，在 A 页 `capture_ui_value` 抓进一个变量，
   到 B 页用 `assert_ui` 配 `${变量名}` 断言。自己读一遍再手打到下一步，正好是错值
   不再可检测的那一步。这个变量域和接口侧共用，所以接口建的数据也能直接拿来断言界面。

## 前置数据：先 mp_use_fixture，再 mp_login_as

用例的 Given 长这样：

```
Given 以 logged-in 状态进入小程序，后端数据用 TC-HOME-001/candidate-mutation
```

执行顺序是**先数据后登录**，两步：

1. `mmcp_wxmp_mp_use_fixture`，把「后端数据用」后面那些名字按顺序传给 `scenes`（收数组）
2. `mmcp_wxmp_mp_login_as`，种登录态

顺序不能反。登录态是照着当前后端数据种的，先登录再换数据，种进去的用户和数据对不上。

Given 里没有「后端数据用」的，用默认 `base`，不要调 `mp_use_fixture`。

片段可以叠加，后面的覆盖前面的同名字段。完整清单见
`mcp_servers/wxmp/fixtures/README.md`。

## 标了 ⛔ 的用例现在不要跑

用例上方带 `# ⛔ 当前不可执行` 注释的，是已经确认当前环境或实现下跑不出结果的
（微信原生弹窗点不到、前端功能没实现、mock 网关造不出那种时序）。注释里写了具体原因。
遇到这种直接跳过并如实报告原因，不要尝试绕过去凑一个通过。

## 输入框与发送按钮

发送按钮**只在输入框有内容时才存在**。空输入时那个位置渲染的是「语音」按钮，
这时候找「发送」必然找不到——不是用例写错，是顺序问题。

所以 `输入「…」` 那一步必须真的生效，再点发送：

1. `mmcp_wxmp_mp_trigger`，`into` 传输入框的 placeholder（对话页是 `请输入消息...`），
   `event` 传 `input`，`detail` 传 `{"value": "要输入的文字"}`
2. 用 `mmcp_wxmp_mp_snapshot` 确认输入框的 `value` 变了、并且「发送」按钮出现了
3. 再 `mmcp_wxmp_mp_tap_text` 点「发送」

第 2 步别省。输入没生效时，第 3 步的报错是「找不到发送」，看上去像按钮文案不对，
实际是上一步没写进去。

## 环境说明

后端是 mock 网关，数据来自固定 fixture。默认 `base` fixture 下已登录用户是昵称 Neo、用户ID
user-001；当 Given 指定了别的 fixture（如 TC-REPORT-001），登录后的昵称/身份以该 fixture 实际
返回的资料为准。不要因为昵称不是 Neo 就判定登录失败或用例不可执行——除非用例的断言本身就是在
验证昵称或身份。
