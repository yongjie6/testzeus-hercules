# 被测对象：ESM V3.0 答题与量表结果接口（esm-assessment，经 esm-miniapp-gateway 暴露）

本套件测的是 HTTP 接口，不是页面。不要打开浏览器，也不要驱动小程序。

契约真源：
- 方法与路径：idl/esm/v1/esm_gateway.proto
- 答题结构：idl/esm/v1/esm_assessment.proto
- 业务错误码：idl/error_code_esm.go
- 调用顺序说明：openspec/changes/add-esm-v21-backend/frontend_api_flow.md §4 §5

## 工具路由

target_helper 固定用 api。本套件只用 `esm_new_user` 和 `esm_call`。

不要用 `generic_http_api`，也不要用浏览器工具。`generic_http_api` 不会带泳道头、不会补
baseReq、也不会带登录态。

## 跨步骤取值：用 ${变量}，不要手抄

用例里的 id 一律不要从上一步的返回里"看着抄"到下一步——那些是
`scale_result_1787579309015_5fc762d981300012` 这种长随机串，抄错一位整条用例就废了，
而且失败现象和接口本身出错分不清。

产生值的那次调用顺手捕获，后面直接引用：

```
调用 POST /api/esm/v1/chat/create，...，用 extract_json 捕获 {"chatId": "$.body.chat.chatId"}
调用 POST /api/esm/v1/chat/message/send，...，body 传 {"chatId": "${chatId}", ...}
```

- `extract_json` 是 `esm_call` / `esm_wait_report` / `esm_wait_chat_reply` 的参数，
  写成 `{"变量名": "JSONPath"}`，路径打到哪匹配不上就直接报错，不会静默留空。
- `${变量}` 可以出现在 `path` / `body_json` / `query_json` 里，请求发出前替换。
- **变量名只能用字母数字下划线**，不能带点——框架的占位符正则是
  `[A-Za-z_][A-Za-z0-9_]*`，写成 `${A.userId}` 匹配不上，会原样发给服务端。

`esm_new_user` 建的用户会自动发布这几个变量，不用捕获：

| 变量 | 内容 |
|---|---|
| `${A_userId}` | 标签 A 的 userId |
| `${A_resultId}` | 标签 A 的量表 resultId（做完量表后才有值） |
| `${A_phone}` | 标签 A 的手机号 |
| `${A_gender}` | 标签 A 的性别枚举（没填资料的用户是空串） |
| `${A_birthDate}` | 标签 A 的出生日期（没填资料的用户是空串） |

标签 B、C 同理，把 A 换成对应标签。

**A、B、C 的性别和出生日期默认是不一样的**，这是故意的：对话和报告工作流现在会同时收到
双方的年龄和性别，两边用同一套属性的话，传错边或者漏传都测不出来。用例需要某个具体取值时
才给 `esm_new_user` 显式传 `gender` / `birth_date`。

## 判定口径

网关对业务失败也返回 HTTP 200。

- 成功：`statusCode == "0"`
- 失败：`statusCode != "0"`，具体原因看 `bizCodeName`

## JSON 约定

- 字段名 lowerCamelCase，int64 是字符串（`"1"`、`"0"`），枚举传全名字符串。
- `questionNo` 和 `choiceValue` 是 int32，传数字。

## 答题规则

- 题号范围 1 到 144，选项值范围 1 到 6。
- 答案必须按题号推进：只能提交已答过的题（改答）或当前题 `session.currentQuestionNo`。
  跳答还没到的题号会被判成题号非法。
- 提交与已保存答案完全相同的选项，按幂等成功处理：`answerVersion` 不递增，
  `modified` 不置 true，`answeredAtMs` 不变。
- 改答已答题：`answerVersion` 递增，`modified` 置 true，后面已答的题不会被清掉。
- 第 144 题通过完整性检查后 `completed` 为 true 并返回 `resultId`。
- `RestartAnswering` 必须带 `confirmed: true`。

## 断言值域用 all_gte / all_lte，别用 gt / lt

`gt` / `lt` 只比路径命中的**第一个**值。`$.body.result.scoreResults[*].score` 打到 16 个
维度分，写 `lt 3` 等于只查了第一维，后面 15 维越界照样判通过——缺陷 7102943924
（16 维分值超出 [-3,3]）正是这个形状：首维在区间内，越界的排在后面。

约束「每个命中值」用 `all_gte` / `all_lte`，失败时会报出第一个越界的下标和值。
`gt` / `lt` 命中多个值时结果里会留 note 点名这件事，不会静默。

## 耗时断言用 esm_latency_probe，不要读单次的 elapsedMs

`esm_call` 现在会在返回里带 `elapsedMs`（本次请求 runner 到网关的往返，含网络）。它便于
排查，但**不适合直接拿来断言**：2026-08-31 在 feat-esm-v3-0 上实测，最便宜的免登录接口
`/runtime/state` p50 是 394ms，p90 却到 1253ms——单次采样分不出真实劣化和抖动。

要断言耗时就用 `esm_latency_probe`：连打 N 次，返回 `minMs / p50Ms / p90Ms / maxMs /
samples / failed`。三条纪律：

- **判 p90，不判 max**，一个离群点不该让整套变红
- **先判 `failed` 是 0**，失败的调用往往在参数校验就返回了，比成功的快得多，混进分布会让
  一个全在报错的接口看起来性能很好
- **阈值来自同泳道同 runner 的实测基线**，不要照搬 PRD 里的服务端耗时指标——那是服务端
  处理时间，这里量的是含网络的往返，两个量混用得到的阈值不是恒红就是恒绿

当前基线（n=10，复用连接）：`/answering/answer` p50 398ms / p90 403ms。

## 前置条件成本

单位成本按 2026-08-26 在 feat-esm-v3-0 泳道实测：

| 前置动作 | 耗时 | 说明 |
|---|---|---|
| 一份量表（`with_scale_result`） | **约 64 秒** | 注册 + 填资料 + 连答 144 题 |
| 等第一份报告（`esm_wait_report`） | **约 120 秒** | Agent 侧异步写回，和量表快慢无关 |
| 同批的其余报告 | **不到 1 秒** | 三种报告一起生成，第一份就绪时其余已经在了 |
| 一轮对话回复 | 不定 | 真实模型生成，没有可写死的数字 |

每条 Scenario 上方的「前置：…」按这张表算出来。量表那一项曾经是 168 秒，
`esm_api._send()` 改成复用连接后降到 64 秒——那 104 秒全是每题重建 TCP+TLS 的开销。
量表耗时再变时改这里的单位成本，各条 Scenario 的标注跟着重算即可。

带「起」字的是下限：那条用例还含对话回复，时长取决于模型。

## 环境说明

默认打测试环境泳道 `feat-esm-v3-0`，由 `ESM_BASE_URL` / `ESM_LANE` 控制。
当前泳道题库是本地开发题库，题干形如「本地开发占位题目 001」，量表标题是
「ESM 本地开发量表」，维度共 16 个。断言维度数量和标题时按这套题库判断。
