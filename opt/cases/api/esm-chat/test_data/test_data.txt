# 被测对象：ESM V3.0 对话接口（esm-chat，经 esm-miniapp-gateway 暴露）

本套件测的是 HTTP 接口，不是页面。不要打开浏览器，也不要驱动小程序。

契约真源：
- 方法与路径：idl/esm/v1/esm_gateway.proto
- 对话结构：idl/esm/v1/esm_chat.proto
- 业务错误码：idl/error_code_esm.go
- 调用顺序说明：openspec/changes/add-esm-v21-backend/frontend_api_flow.md §7

## 工具路由

target_helper 固定用 api。本套件用 `esm_new_user`、`esm_call`、`esm_wait_report`、
`esm_wait_chat_reply` 和 `esm_risk_sample`。

不要用 `generic_http_api`，也不要用浏览器工具。

## 跨步骤取值：用 ${变量}，不要手抄

用例里的 id 一律不要从上一步的返回里"看着抄"到下一步——那些是
`scale_result_1787579309015_5fc762d981300012` 这种长随机串，抄错一位整条用例就废了，
而且失败现象和接口本身出错分不清。

产生值的那次调用顺手捕获，后面直接引用：

```
调用 POST /api/esm/v1/chat/create，...，用 extract_json 捕获 {"chatId": "$.body.chat.chatId"}
调用 POST /api/esm/v1/chat/message/send，...，body 传 {"chatId": "${chatId}", ...}
```

- `extract_json` 是 `esm_call` / `esm_wait_report` / `esm_wait_chat_reply` 的参数，
  写成 `{"变量名": "JSONPath"}`，路径打到哪匹配不上就直接报错，不会静默留空。
- `${变量}` 可以出现在 `path` / `body_json` / `query_json` 里，请求发出前替换。
- **变量名只能用字母数字下划线**，不能带点——框架的占位符正则是
  `[A-Za-z_][A-Za-z0-9_]*`，写成 `${A.userId}` 匹配不上，会原样发给服务端。

`esm_new_user` 建的用户会自动发布这几个变量，不用捕获：

| 变量 | 内容 |
|---|---|
| `${A_userId}` | 标签 A 的 userId |
| `${A_resultId}` | 标签 A 的量表 resultId（做完量表后才有值） |
| `${A_phone}` | 标签 A 的手机号 |
| `${A_gender}` | 标签 A 的性别枚举（没填资料的用户是空串） |
| `${A_birthDate}` | 标签 A 的出生日期（没填资料的用户是空串） |

标签 B、C 同理，把 A 换成对应标签。

**A、B、C 的性别和出生日期默认是不一样的**，这是故意的：对话和报告工作流现在会同时收到
双方的年龄和性别，两边用同一套属性的话，传错边或者漏传都测不出来。用例需要某个具体取值时
才给 `esm_new_user` 显式传 `gender` / `birth_date`。

## 判定口径

网关对业务失败也返回 HTTP 200。

- 成功：`statusCode == "0"`
- 失败：`statusCode != "0"`，具体原因看 `bizCodeName`

## JSON 约定

- 字段名 lowerCamelCase，int64 是字符串（`seqId` 是 `"1"` 这种），枚举传全名字符串。

## 领域规则

- 自己的对话用 `CreateChat`，`chatKind` 传 `CHAT_KIND_SELF`；关系对话用
  `StartRelationshipChat`，不能用 `CreateChat` 建。
- 每次发送都带 `clientRequestId`。同一个值重发同样的内容按幂等成功处理；同一个值换内容
  返回 `BIZ_ESM_CHAT_CLIENT_REQUEST_CONFLICT`。
- 一轮的服务端顺序是：输入审核、生成、输出审核、最终助手消息落库。落库前同一对话不接受
  下一条。`turnStatus`、`auditStage`、`replySource` 分别表达当前轮状态、审核阶段和回复来源。
- 流式增量走 WebSocket，最终内容以落库消息为准。本套件不测 WebSocket，用
  `GetMessagesAfterSeq` 读落库结果，也就是前端断线重连的补偿读取路径。
- `seqId` 是已落库消息序号，助手回复落库后才推进。
- 首次进入关系对话，服务端按顺序推两条初始化消息：固定开场白，然后是对方报告。
- 关系选择卡片提交时 `relationshipInputResponse` 传 true；选项型同时带
  `relationshipTypeSelection`，服务端按关系类型树校验。
- 推荐问题是旁路卡片，最终助手消息落库后异步生成，通过
  `GetChatDetail.activeRecommendedQuestionCard` 或 `GetRecommendedQuestionCard` 读取。
- 删除会话只影响当前用户的会话列表可见性。
- `StartRelationshipChat.createNewChat` 是 optional。**进候选关系对话时省略这个字段**：
  省略和 false 一样，都是「进入或恢复最近一段关系对话」；true 是用户显式再开一段。
- 编辑重发和重新生成都是换分支，不是追加：
  - `EditAndResendChatMessage` 提交一条**新的**用户消息，原来那条用户消息和它的助手回复
    一起退出当前分支；
  - `RegenerateChatMessage` 只换助手那一条，用户消息留在分支上，旧的助手回复退出。
  - 退出分支的消息在 `GetChatDetail` 和 `GetMessagesAfterSeq` 里都读不到——这两个接口
    返回的是当前分支，不是全部历史。
- 两个接口的助手回复都可能是异步的（响应里 `assistantMessage` 为空、`turnStatus` 是
  `CHAT_TURN_STATUS_GENERATING`），断言最终回复一律走 `esm_wait_chat_reply`。

## StopChatGeneration 为什么没有用例

`SendChatMessage` 的 HTTP 请求会一直挂到这一轮结束才返回（响应里直接带最终的
`assistantMessage`）。`esm_call` 是同步的，等它返回时这一轮已经没有东西可停了，
所以停止生成没法用现在这套工具写——要覆盖它得先给 `additional_tools/esm_api.py`
加一个后台发消息的工具，拿到 `generationId` 之后再调停止。缺的断言是：
`turnStatus` 回到 `CHAT_TURN_STATUS_IDLE`，且被停掉的那一轮不落库助手消息。

## 前置条件成本

单位成本按 2026-08-26 在 feat-esm-v3-0 泳道实测：

| 前置动作 | 耗时 | 说明 |
|---|---|---|
| 一份量表（`with_scale_result`） | **约 64 秒** | 注册 + 填资料 + 连答 144 题 |
| 等第一份报告（`esm_wait_report`） | **约 120 秒** | Agent 侧异步写回，和量表快慢无关 |
| 同批的其余报告 | **不到 1 秒** | 三种报告一起生成，第一份就绪时其余已经在了 |
| 一轮对话回复 | 不定 | 真实模型生成，没有可写死的数字 |

每条 Scenario 上方的「前置：…」按这张表算出来。量表那一项曾经是 168 秒，
`esm_api._send()` 改成复用连接后降到 64 秒——那 104 秒全是每题重建 TCP+TLS 的开销。
量表耗时再变时改这里的单位成本，各条 Scenario 的标注跟着重算即可。

带「起」字的是下限：那条用例还含对话回复，时长取决于模型。

## 环境说明

默认打测试环境泳道 `feat-esm-v3-0`，由 `ESM_BASE_URL` / `ESM_LANE` 控制。
当前泳道接的是真实模型，助手回复内容不可预期，断言只看结构、状态和来源，不要断言正文文案。

**风控用例是这条规则唯一的例外**（TC-ESM30-CH-17/18/19）：那三条断言的不是模型自由发挥的
回复，是产品写死的固定兜底话术、或 PRD 明文规定必须出现的两条热线号码/名称——这些是契约，
不是模型输出，断言正文文案在这里是对的。

## 风控用例的前置数据

心理安全（TC-ESM30-CH-17）只用 prompt 处理，不接外部审核系统，PRD 给出的自伤倾向样例语料
本身是安全的，直接写在了 feature 文件里。

政治安全（TC-ESM30-CH-18/19）接的是真实的外部审核系统，会稳定命中的语料只能由风控/安全团队
提供，不能写进仓库——写死一句真会触发外部审核的文本，等于把"已知能骗过审核系统"的样本发布
出去。这两条用例通过 `esm_risk_sample` 在运行时从环境变量取语料：

```
ESM_RISK_SAMPLE_POLITICAL_INPUT   # 输入侧命中：第一道审核就应该拦
ESM_RISK_SAMPLE_POLITICAL_OUTPUT  # 输出侧命中：能骗过第一道，诱导模型给出应被第二道拦下的回复
```

不设就直接报错说明原因，不会静默跳过或用占位内容代替。要跑这两条，先找风控/安全团队要
一份当前配置下确实会命中的样例。
