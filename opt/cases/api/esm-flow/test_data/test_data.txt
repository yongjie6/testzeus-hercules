# 被测对象：ESM V3.0 小程序服务端场景化串联（跨 gateway / assessment / profile / chat）

本套件测的是 HTTP 接口串起来的完整用户链路，不是页面。不要打开浏览器，也不要驱动小程序。

契约真源：
- idl/esm/v1/esm_gateway.proto、esm_assessment.proto、esm_profile.proto、esm_chat.proto
- idl/error_code_esm.go
- openspec/changes/add-esm-v21-backend/frontend_api_flow.md（总流程时序图 + §1 到 §7）
- openspec/changes/add-esm-v21-backend/tech_design.md（答题到报告状态流、关系链路）

单接口的参数边界和错误码在 esm-gateway / esm-assessment / esm-profile / esm-chat 四个套件里
逐个覆盖。本套件只管一件事：把接口按真实调用顺序串起来，验证跨服务的状态推进是对的。

## 工具路由

target_helper 固定用 api。本套件用这五个工具：

- `esm_new_user`：开一个新账号当链路起点。
- `esm_call`：链路上的每一次接口调用。
- `esm_finish_assessment`：把当前用户剩下的题答完（144 题逐题提交，约 1 分钟）。
- `esm_wait_report`：等 Agent 把报告写回。
- `esm_wait_chat_reply`：等助手回复落库。

不要用 `generic_http_api`，也不要用浏览器工具。

## 跨步骤取值：用 ${变量}，不要手抄

用例里的 id 一律不要从上一步的返回里"看着抄"到下一步——那些是
`scale_result_1787579309015_5fc762d981300012` 这种长随机串，抄错一位整条用例就废了，
而且失败现象和接口本身出错分不清。

产生值的那次调用顺手捕获，后面直接引用：

```
调用 POST /api/esm/v1/chat/create，...，用 extract_json 捕获 {"chatId": "$.body.chat.chatId"}
调用 POST /api/esm/v1/chat/message/send，...，body 传 {"chatId": "${chatId}", ...}
```

- `extract_json` 是 `esm_call` / `esm_wait_report` / `esm_wait_chat_reply` 的参数，
  写成 `{"变量名": "JSONPath"}`，路径打到哪匹配不上就直接报错，不会静默留空。
- `${变量}` 可以出现在 `path` / `body_json` / `query_json` 里，请求发出前替换。
- **变量名只能用字母数字下划线**，不能带点——框架的占位符正则是
  `[A-Za-z_][A-Za-z0-9_]*`，写成 `${A.userId}` 匹配不上，会原样发给服务端。

`esm_new_user` 建的用户会自动发布这几个变量，不用捕获：

| 变量 | 内容 |
|---|---|
| `${A_userId}` | 标签 A 的 userId |
| `${A_resultId}` | 标签 A 的量表 resultId（做完量表后才有值） |
| `${A_phone}` | 标签 A 的手机号 |
| `${A_gender}` | 标签 A 的性别枚举（没填资料的用户是空串） |
| `${A_birthDate}` | 标签 A 的出生日期（没填资料的用户是空串） |

标签 B、C 同理，把 A 换成对应标签。

**A、B、C 的性别和出生日期默认是不一样的**，这是故意的：对话和报告工作流现在会同时收到
双方的年龄和性别，两边用同一套属性的话，传错边或者漏传都测不出来。用例需要某个具体取值时
才给 `esm_new_user` 显式传 `gender` / `birth_date`。

## 判定口径

网关对业务失败也返回 HTTP 200。

- 成功：`statusCode == "0"`
- 失败：`statusCode != "0"`，具体原因看 `bizCodeName`

## JSON 约定

- 字段名 lowerCamelCase，int64 是字符串，枚举传全名字符串。

## 链路顺序

小程序主链路是：

运行时状态 → 登录 → 首页状态 → 资料填写 → 答题 → 量表结果 → 报告 → 已读/反馈
→ 自己的对话 → 推荐问题

关系链路是：

A 完成量表 → A 创建分享 → B 从分享进入并完成量表 → 绑定分享 → 双方候选关系
→ A 进入关系对话（占席位）→ 两条初始化消息 → 关系选择卡片 → 关系对话

`entryStage` 是服务端算好的入口阶段，三个取值依次对应资料填写、答题、首页：
`HOME_ENTRY_STAGE_COMPLETE_USER_INFO`、`HOME_ENTRY_STAGE_ANSWERING`、`HOME_ENTRY_STAGE_HOME`。

## 成本

除断点续答和重新开始外，本套件的用例都要现做量表。单位成本（2026-08-26 实测）：
一份量表约 64 秒，等第一份报告另计约 120 秒（Agent 侧异步，和量表快慢无关）。
排期跑之前先算清楚总时长。
